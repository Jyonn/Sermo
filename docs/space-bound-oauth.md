# Space-bound OAuth (opt-in)

## Teacher bootstrap (0086)

For teacher creation, POST the same seven OAuth parameters and `purpose:"space_admin"` **without a space_id key**. Explicit null/invalid IDs are rejected. The existing approved admin-proof capability is required; no new scope/permission is added. Metadata initially returns `target_space:null`. The provider offers space-scoped cached identities and its administrator login, never a global administrator account. Administrator login can resume via the existing official-login ticket without granting OAuth consent. At the explicit consent POST (still ONLY request_id), the provider atomically selects the authenticated official account's own space, verifies current administrator identity and double verification, and creates the bound grant. Failures leave the bootstrap unbound. After this point code, token and userinfo use the same strict frozen-space policy as before. No browser-supplied space selection is accepted. Students (`purpose:join`) still require a fixed integer space_id. Consumer must accept the proved space only for its teacher-create transaction, and atomically create/bind the group after validating state/PKCE/sub/email/proof; existing fixed-space invitations must not use discovery mode.

No new scopes. Existing OAuth clients and grants remain valid. Userinfo adds integer `space_id`; email is normalized. All authorization, code exchange and userinfo still require the existing email AND phone verification.

Enable the protocol with `OAUTH_SPACE_REQUESTS_ENABLED=1` only after migration 0085. POST `/users/oauth/requests` with the existing seven authorization parameters plus integer `space_id` and optional `purpose` (`join`, default; or `space_admin`). Response 201: `request_id`, `expires_in:1800`, `authorization_url` on `https://frienden.jyonn.space/oauth/authorize` containing only request_id. No client secret is required for this public PKCE request, and creating a request does not authorize anything. Keep request IDs out of logs. Apply ingress rate limits to this public endpoint.

GET `/users/oauth/metadata?request_id=...` returns normal client metadata plus frozen `parameters`, `target_space:{id,slug,name}` and `purpose`. POST `/users/oauth/authorize` accepts ONLY `{request_id}` with the user's ordinary Frienden bearer session. Same-space, current double verification and explicit user consent remain mandatory. Wrong-space or unverified attempts do not consume the request. Cancel with POST `/users/oauth/requests/cancel` and `{request_id}`. Used/cancelled/expired requests cannot resume. Code and access-token validation retain and enforce the target space.

Admin proof requires the separate application capability `space_admin_proof_enabled` (default false for ALL clients). Platform administrator registry action `{action:"admin_proof",version:<current>,enabled:true}` is audited and concurrency checked; this is a specific persistent capability grant requiring operator approval. Do not enable it while deploying code. `space_admin` also requires the current official user to match the space's `official_user_id` at consent, exchange and userinfo. Only these grants return `space_admin:true`. This proof does NOT grant any space management APIs or remove the need to revalidate a binding later. Normal joins never return this claim.

Consumer: freeze invite/group/binding revision, space, state, PKCE verifier, browser session and expiry on your backend. Validate response URL, then state, token and userinfo; require matching integer space_id, stable sub, verified normalized email. Subject/email conflicts require existing-account confirmation, never automatic takeover. This conflict handling belongs to the consumer, not the provider. Do not request phone scope just to satisfy eligibility.

Registration and verification resume the same request_id through the existing same-origin pending and account-security return flow. A request lasts 30 minutes; expiry requires a fresh consumer flow. No passwords, hashes, verification flags, or preprovisioned identities are shared.

Tests use `--settings=Sermo.isolated_test_settings` and an in-memory database, no deployment settings/secrets or real mail. Migration is additive with no data backfill; existing capabilities remain false. Before production migration, take an operator-controlled database backup, record applied migration/head and current service unit. Roll back code with protocol disabled first; prefer retaining additive tables/nullable fields. Do not reverse schema after live bound grants exist without a reviewed data-retention plan. No production migration or capability grant is performed by this document.
